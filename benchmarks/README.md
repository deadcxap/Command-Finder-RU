# Сравнение моделей поиска команд

Бенчмарк сравнивает качество поиска, задержки и память с исходным проектом. Он использует сохранённый снимок поиска `benchmarks.legacy.search` и SQLite/sqlite-vec: выборку `2 × top_k` паттернов и удаление повторов по точному шаблону команды. Меняется энкодер и выбранный словарь. Шаблоны команд остаются данными и не исполняются.

Для повторения эксперимента используется замороженный английский словарь из `benchmarks/data/original` и согласованные русские варианты из `benchmarks/data/russian-variants.json`. Это отдельные данные бенчмарка: рабочий словарь приложения в `src/cf/data/commands` уже содержит русские формулировки. Исторический загрузчик исходной MiniLM сохранён отдельно внутри `benchmarks`; рабочее приложение использует mini-retriever.

Рабочая база, модель и JSON исходного приложения не изменяются. Каждый запуск работает в отдельном процессе со своей базой и кешем запросов; артефакты по умолчанию сохраняются в `.benchmarks`. Кеш весов общий для запусков внутри проекта.

## Быстрая проверка

Запускать из корня проекта в WSL, используя Linux Python 3.12+. В примерах `python` обозначает интерпретатор активного виртуального окружения проекта.

```bash
python -m benchmarks validate
python -m benchmarks profiles
python -m unittest benchmarks.test_metrics benchmarks.test_runner
```

Валидация набора и проверка метрик используют стандартную библиотеку, не скачивают веса и не требуют PyTorch. Для реального поиска нужны зависимости проекта, в частности `numpy` и `sqlite-vec`; для моделей — `sentence-transformers`. Режим исходного ONNX также требует `onnxruntime` и токенизатор.

Для отдельного CPU-окружения в WSL можно сначала установить CPU-сборку PyTorch из [официального репозитория](https://pytorch.org/get-started/locally/), затем зависимости проекта:

```bash
/usr/bin/python3 -m venv .venv
.venv/bin/python -m pip install 'torch==2.6.0' --index-url https://download.pytorch.org/whl/cpu
.venv/bin/python -m pip install -c benchmarks/constraints-cpu.txt -e '.[dev,benchmark]'
.venv/bin/python -m unittest discover -s benchmarks -p 'test_*.py'
```

Полная проверка бенчмарка использует снимок `benchmarks.legacy.search` и sqlite-vec с тестовым энкодером и не загружает веса. Это сохраняет контроль исходного поведения независимо от последующих изменений рабочего `cf.search`. Приведённые ниже команды реального измерения следует выполнять тем же интерпретатором окружения.

Проверенная CPU-связка закреплена в `constraints-cpu.txt`. Для реальных моделей требуется дополнительный набор зависимостей `.[benchmark]`; обычному поиску он не нужен. Фактически установленные версии своего окружения можно сохранить через `python -m pip freeze --all`; версии опубликованного прогона находятся в исходных отчётах в `docs/benchmarks/raw-reports.json.gz`. Для USER2 профиль явно передаёт `config_kwargs={"reference_compile": false}`, чтобы не включать автоматическую компиляцию на CPU. Настройка и её фактическое значение сохраняются в метаданных.

Загрузки моделей по умолчанию запрещены. Если нужных весов ещё нет в кеше бенчмарка, запуск завершится с объяснением; `--download` явно разрешает их загрузку. Автоматического обучения, ONNX-экспорта и квантизации нет.

## Полный прогон после клонирования

После установки CPU-зависимостей выполните из корня репозитория:

```bash
python -m benchmarks.prepare --profiles benchmarks/pinned-profiles.json --download --corpora ru2
python -m benchmarks.export_onnx
python -m benchmarks.native_export --out .benchmarks --download
CF_BENCH_NATIVE_ONNX="$(python -c 'import json; from pathlib import Path; print(json.loads(Path(".benchmarks/native-original-onnx/latest.json").read_text())["onnx_dir"])')"
python -m benchmarks.suite --native-onnx "$CF_BENCH_NATIVE_ONNX"
```

Закреплённые профили входят в репозиторий: `benchmarks/pinned-profiles.json`. `export_onnx` использует их по умолчанию и после успешного экспорта всех 12 артефактов автоматически создаёт `.benchmarks/onnx-ready.json`, который читает `suite`.

`native_export` подготавливает штатный ONNX исходного проекта; результат и сведения о происхождении находятся в отдельном каталоге под `.benchmarks/native-original-onnx`. Файл `latest.json` содержит поля `onnx_dir` и `info_path`. По умолчанию экспорт работает без сети; `--download` нужен, если исходные веса ещё отсутствуют в кеше. Для исторического загрузчика ссылка `refs/main` в изолированном кеше бенчмарка устанавливается на закреплённую ревизию MiniLM; это отражено в `info.json`.

Готовый прогон указан в `.benchmarks/suites/latest.json`. Для его сводки:

```bash
CF_BENCH_MANIFEST="$(python -c 'import json; from pathlib import Path; print(json.loads(Path(".benchmarks/suites/latest.json").read_text())["manifest_path"])')"
python -m benchmarks.summarize "$CF_BENCH_MANIFEST" --out .benchmarks/results
```

## Подготовка моделей и индексов

Подготовка скачивает выбранные профили, строит отдельные индексы и проверяет загрузку каждой модели без сети в новом процессе. Полный прогон оценок качества здесь не запускается:

```bash
python -m benchmarks.prepare --download --corpora ru2 --threads 2 --batch-size 32
python -m benchmarks.prepare --models original --corpora original
```

Первый запуск по умолчанию включает все шесть профилей. Через `--models` можно выбрать подмножество; `--corpora original ru1 ru2` готовит несколько словарей для каждой выбранной модели. Для общего сравнения моделей нужен одинаковый корпус, например `ru2`; исходный английский контроль готовится отдельно.

Каждая подготовка получает новый идентификатор. Индексы и журналы находятся в `.benchmarks/prepared/<профиль>/<идентификатор>/<корпус>`, общий манифест и закреплённые профили — в `.benchmarks/prepared/collections/<идентификатор>`. `.benchmarks/prepared/latest.json` указывает на последний манифест. Существующие индексы не перезаписываются.

После первого получения весов конкретной модели её дальнейшие корпусы и проверки запускаются без сети на закреплённом commit SHA. Проверяется совпадение выдачи обычного поиска и нового процесса с кешем, который не загружает модель. `status: ready` в манифесте означает успешную подготовку; при сбое сохраняются ошибка, журналы и уже подготовленные модели, а команда возвращает ненулевой код. Наличие файлов весов само по себе не считается успешной проверкой.

При частичном сбое файл закреплённых ревизий может содержать уже скачанные веса модели, чья проверка не завершилась; готовность конкретного индекса определяется статусом соответствующей задачи в манифесте.

Файл `pinned-profiles.json` позволяет повторять измерения на тех же ревизиях. С ним нужно явно выбрать управляемый backend, в том числе для исходной модели:

```bash
python -m benchmarks run --profile tiny-retriever --corpus ru2 --backend sentence-transformers --profiles .benchmarks/prepared/collections/<идентификатор>/pinned-profiles.json
```

У неизменённого backend `project` оригинальный загрузчик принимает `main`; его фактическая ревизия фиксируется в отчёте. Подготовка использует Sentence Transformers и не меняет рабочую модель приложения, не экспортирует ONNX и не квантизует веса.

## ONNX и 8-битные варианты

После скачивания и закрепления ревизий можно отдельно экспортировать все модели. Эта команда работает без сети и не запускает сравнительный бенчмарк:

```bash
.venv/bin/python -m benchmarks.export_onnx --profiles benchmarks/pinned-profiles.json --threads 2 --max-tokens 128
```

Экспорт получает новый идентификатор. В `.benchmarks/onnx/<профиль>/<идентификатор>/fp32` и `int8` лежат самостоятельные `model.onnx`, `tokenizer.json` и `metadata.json`. Манифест находится в `.benchmarks/onnx/collections/<идентификатор>/manifest.json`; `latest.json` указывает на последнюю коллекцию. Только `status: ready` подтверждает успешный экспорт и проверки. Неудачные коллекции сохраняются с ошибками и журналами.

Граф содержит весь путь Sentence Transformers, включая pooling, дополнительные модули и L2-нормализацию. Входы имеют динамические размеры пакета и последовательности, выход — `sentence_embedding` размерности 312 или 384. Префиксы запросов и описаний, токенизация, ревизия весов и предел длины сохраняются в метаданных. Для USER2 явно отключена компиляция и используется eager attention. Вычисления экспортированного графа требуют NumPy, Tokenizers и ONNX Runtime; PyTorch и Sentence Transformers нужны для экспорта и проверки эталона.

Вариант `int8` использует динамическое квантование U8U8 (`QUInt8`, per-channel, полный диапазон) для линейных слоёв и таблиц эмбеддингов (`MatMul`, `Gemm`, `Gather`). Имя каталога обозначает 8-битный вариант; веса хранятся в **uint8**, выходные векторы — float32. Pooling, нормализация и часть остальных операций сохраняют float32. Такой выбор избегает проблемы насыщения U8S8 на некоторых CPU, описанной в [документации ONNX Runtime](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html). Тип квантования и реальные размеры файлов записываются в результат.

Проверка экспорта использует восемь технических строк, включая русский и английский, пустой ввод, пробелы и длинный текст, оба префикса и пакеты 1/3/8. Проверяются структура ONNX, реальные 8-битные операции, размерности, конечность и нормы векторов. Для FP32 требуется cosine не ниже 0.99999 и максимальная абсолютная ошибка не больше 1e-4 относительно PyTorch; для 8-битного варианта — cosine не ниже 0.97. Это технический порог подготовки, который не гарантирует сохранение качества поиска. Все измерения поиска на наборе запросов выполняются отдельным последующим запуском.

Для будущего измерения выбранного артефакта используется отдельный backend:

```bash
.venv/bin/python -m benchmarks run --profile tiny-retriever --profiles benchmarks/pinned-profiles.json --corpus ru2 --languages ru en --backend onnx --onnx-dir .benchmarks/onnx/tiny-retriever/<идентификатор>/int8 --threads 2
```

Этот запуск создаёт собственный индекс векторами выбранного ONNX-варианта. Смешивать векторы документов из PyTorch с запросами из квантованной модели при сравнении не следует. Полный sentence-encoder имеет другой формат выхода, чем исходный `project --onnx-dir`, который ожидает `token_embeddings`; для новых артефактов нужен `--backend onnx`.

## Контроль исходного проекта

Сначала измерить исходную модель на исходном английском словаре отдельно с русскими и английскими запросами:

```bash
python -m benchmarks run --profile original --corpus original --languages ru en --backend project --download
```

Английский результат показывает, как исходник решает привычную ему задачу. Русский — исходный уровень поддержки русского. Они нужны оба: сравнение только русских запросов не показывает возможную регрессию английского поиска.

Для воспроизведения существующего ускоренного пути можно передать готовую ONNX-модель из Linux-каталога:

```bash
python -m benchmarks run --profile original --corpus original --languages ru en --backend project --onnx-dir /home/user/cf-onnx --project-initial-seed
```

Без переданной ONNX-модели исходный путь использует свой обычный Sentence Transformers fallback. У исходного ONNX ограничение длины 128 токенов; у штатного `all-MiniLM-L6-v2` в fallback — 256. Эти настройки сохраняются для контроля оригинала. Управляемое сравнение энкодеров ниже задаёт общий предел 128 токенов.

Исходный ONNX фиксирует четыре CPU-потока: при передаче `--onnx-dir` это также значение по умолчанию в бенчмарке. Явное другое число потоков отвергается. `--project-initial-seed` воспроизводит первый запуск исходной CLI: сначала индекс строится через ST с пределом 256 токенов и пакетами 128, затем перед поиском устанавливается штатный ONNX. В отчёте отдельно сохраняются настройки индексации и поиска. Это также исключает старый путь повторной ONNX-индексации, который передаёт весь словарь одним пакетом и игнорирует размер пакета. Управляемые ST/ONNX-варианты используют `--batch-size` (по умолчанию 32).

Разницу между исходным ONNX и PyTorch-кандидатом нельзя приписывать только модели. Для сравнения самих энкодеров нужен контроль с тем же backend:

```bash
python -m benchmarks run --profile original --corpus original --languages ru en --backend sentence-transformers --download
```

## Сравнение моделей и словарей

| Корпус | Что индексируется |
|---|---|
| `original` | Все 1 946 английских паттернов из `benchmarks/data/original` |
| `ru1` | Первый согласованный русский вариант каждого сценария: 1 946 паттернов |
| `ru2` | Оба согласованных русских варианта: 3 892 паттерна |
| `mixed` | Исходные английские паттерны вместе с `ru2` |

`original` использует снимок исправленного английского словаря до переноса русских формулировок в приложение. Исторический Git commit, хеши исходных файлов и прежние значения изменённых сценариев сохранены в [журнале исправлений](../docs/command-fixes.json). Эталоны запросов и русский набор синхронизированы с этим снимком. Старые отчёты с прежней версией запросов требуют повторного прогона.

Сравнивать модели следует на одинаковом корпусе, с одним backend и одинаковыми параметрами запуска. Эффект второго варианта описания измеряется отдельным сравнением `ru1` и `ru2` при неизменной модели. Иначе улучшение от дополнительных формулировок смешивается с улучшением энкодера.

```bash
python -m benchmarks run --profile original --corpus ru1 --languages ru en --backend sentence-transformers --download
python -m benchmarks run --profile tiny-retriever --corpus ru1 --languages ru en --backend sentence-transformers --download
python -m benchmarks run --profile mini-retriever --corpus ru1 --languages ru en --backend sentence-transformers --download
python -m benchmarks run --profile user2-small --corpus ru1 --languages ru en --backend sentence-transformers --download
```

После сравнения моделей проверить расширение словаря для выбранного кандидата:

```bash
python -m benchmarks run --profile tiny-retriever --corpus ru2 --languages ru en --backend sentence-transformers
```

В `profiles.json` также есть `tiny2` и `e5-small`. Sentence Transformers читает pooling из конфигурации модели. Для USER2 указаны `search_query: ` и `search_document: `. У E5 обе стороны получают `query: `, поскольку паттерны — короткие перефразировки намерений; это режим симметричного поиска из [карточки E5](https://huggingface.co/intfloat/multilingual-e5-small). Любой другой выбор префиксов — отдельный эксперимент, его следует сохранить в отдельном профиле.

Общие параметры:

```bash
python -m benchmarks run --profile tiny-retriever --corpus ru1 --languages ru en --backend sentence-transformers --threads 2 --repeats 3 --batch-size 32 --max-tokens 128 --top-k 7 --out .benchmarks
```

Для воспроизводимости сохранять настройки, версии библиотек, сведения об оборудовании и исходные отчёты. `revision: main` в начальных профилях — изменяемая ссылка. Для закреплённого эксперимента заменить её конкретным commit SHA модели и сохранить профиль вместе с результатами. Не менять профили между сравниваемыми повторами незаметно.

## Набор запросов и метрики

`queries.json` содержит 96 пар русских и английских запросов: 90 задач во всех 15 категориях и 6 запросов вне области словаря. Среди задач есть разговорные варианты, опечатки, смешение с техническими терминами и контрастные операции. Эталоны — точные шаблоны команд; для части случаев также перечислены заведомо неподходящие шаблоны.

Проверка запрещает точные нормализованные совпадения запросов с индексируемыми описаниями. Это проверка утечки текста, а не доказательство независимости смысловых задач: эталоны и допустимые альтернативы стоит вычитать перед использованием результата для окончательного выбора. Исправления набора требуют повторного прогона всех сравниваемых конфигураций.

- **Hit@1/3/5/7** — доля задач, где хотя бы один допустимый шаблон попал в первые K результатов. Основной критерий удобства — Hit@3.
- **MRR@7** — насколько высоко находится первый подходящий шаблон; результаты ниже седьмого места считаются промахом.
- **Recall@K** и **nDCG@K** — покрытие размеченных подходящих шаблонов и качество их порядка. Эталоны могут содержать несколько допустимых альтернатив.
- **Forbidden-hit@1/3** — попадание явно запрещённого для этой задачи шаблона. Знаменатель — только задачи с заполненным списком запретов; меньше лучше.
- Разрезы по категориям и тегам помогают найти регрессии, скрытые общей средней. Macro-оценка даёт категориям одинаковый вес.

Шесть запросов вне области словаря выводятся отдельно. Исходный поиск всегда предлагает команды и не имеет порога отказа, поэтому эти случаи не оцениваются как способность правильно отказаться от ответа.

Качество измеряется без использования ранее рассчитанного вектора запроса. Прогретый поиск без кеша и повторный запрос с попаданием в кеш следует читать отдельно. В оригинале нормализация ключа удаляет английские `not/no` и сортирует слова: одинаковый ключ не гарантирует одинакового намерения. Этот эффект нельзя скрывать попаданиями в кеш в основной оценке качества.

«Холодный» запуск здесь означает новый процесс с незагруженной моделью. Это не очистка файлового кеша Linux. Время скачивания весов следует отделять от времени запуска и поиска. CPU, число потоков, длина текста, размер пакета и backend должны совпадать, когда сравнивается скорость моделей.

Скачивание разрешено только на подготовительном этапе. Холодный и прогретый замеры всегда работают без сети. Первый `prepare.model_load_ms` с `--download` может включать получение весов; его нельзя считать чистым временем загрузки модели с диска.

Для каждого языка дополнительно запускается новый процесс с уже закешированным вектором первого запроса. Фаза `cached-cold` проверяет наличие кеша и выполняет поиск без загрузки модели. Это отдельный показатель от `cache_hit` в прогретом процессе, где модель уже находится в памяти. `--repeats` повторяет прогретые замеры; на язык приходится одна проба каждого нового процесса. Для устойчивой оценки запуска нужно повторить полный `run` несколько раз.

Измеряется общий для всех моделей процесс поиска без интерактивного меню и shell-виджета. Это воспроизводимый замер ядра поиска, а не полная задержка нажатия Ctrl+F в терминале.

## Отчёты

Полная подготовленная матрица запускается последовательно:

```bash
python -m benchmarks.suite --native-onnx "$CF_BENCH_NATIVE_ONNX"
python -m benchmarks.summarize .benchmarks/suites/<идентификатор>/manifest.json --out .benchmarks/suites/<идентификатор>/results
```

Матрица содержит 22 конфигурации: шесть моделей × PyTorch/ONNX FP32/8-битный ONNX на `ru2`, два исходных режима на английском словаре (штатный ONNX и ST fallback) и два английских контроля MiniLM с управляемым ST/ONNX. Прогретые измерения повторяются трижды для каждого из 96 запросов на каждом языке. Для холодного и холодного с кешем запускается по три новых процесса на язык; в сводке показывается медиана, для RSS — максимум. Модели запускаются по очереди, без конкурирующих модельных измерений.

`summarize` создаёт JSON, CSV и самостоятельный HTML с полной таблицей, графиками и изменениями относительно исходного ONNX. Качество считается по 90 задачам на язык; шесть запросов вне словаря выводятся отдельно. Разница в одну задачу соответствует примерно 1,11 процентного пункта Hit@3. Запросы и эталоны фиксируются до прогона и не подгоняются под результаты.

Каждый запуск сохраняет отчёт в своём каталоге под `.benchmarks/runs`. Сравнение готовых отчётов не требует загрузки моделей:

```bash
python -m benchmarks compare .benchmarks/runs/first/report.json .benchmarks/runs/second/report.json
```

Сначала сопоставлять качество на одинаковых запросах, затем время запуска, задержки поиска и пиковую память. Рост Hit@3 ценой заметно более тяжёлого запуска может быть невыгоден для короткоживущей консольной утилиты. Полученные на другой машине миллисекунды и память напрямую не переносить.

`bad@3` в таблице — `forbidden_hit@3`. `inference MiB` — максимум RSS холодного и прогретого процессов поиска; память построения индекса находится отдельно в `prepare.peak_rss_bytes`, а память запуска с кешем — в `cached_cold.<язык>.peak_rss_bytes`. Отчёт также содержит версии библиотек, фактический backend, dtype, ревизию весов, настройки и хеши исходного приложения и кода бенчмарка. Сравнение отвергает разные версии набора запросов и отмечает различия условий измерения.

## Стоимость адаптации

Для первого сравнения используются готовые энкодеры, обучение не нужно. Индексацию нескольких тысяч коротких описаний можно выполнить на CPU; GPU не обязателен. При 3 892 записях сами float32-векторы занимают около 4,63 МиБ для размерности 312 или 5,70 МиБ для 384, без накладных расходов базы.

Веса tiny-retriever, mini-retriever, USER2-small и E5-small вместе занимают примерно 831 МБ; исходная модель добавляет около 90 МБ, необязательный tiny2 — ещё около 118 МБ. Окружение Python/PyTorch, кеши и будущие ONNX-копии требуют дополнительного места. Для разработки разумно предусмотреть несколько гигабайт свободного диска и памяти и загружать модели последовательно. Это предварительный запас, а не измеренный минимум или обещание скорости.

Для BERT-кандидатов основная работа — правильные pooling, токенизация, размерность, кеши и проверка ONNX. USER2 основан на ModernBERT, поэтому текущая ручная BERT-обёртка экспорта потребует замены или отдельного пути; совпадение размерности 384 не делает модели совместимыми. Подключение через Sentence Transformers позволяет сначала сравнить качество без этой переделки.

Динамическую INT8-квантизацию можно рассмотреть после базового сравнения: она не требует калибровочного датасета, но её выигрыш и изменение качества нужно измерять отдельно. Официальные источники: [Sentence Transformers](https://sbert.net/docs/sentence_transformer/usage/efficiency.html), [ONNX Runtime](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html), [USER2-small](https://huggingface.co/deepvk/USER2-small).
