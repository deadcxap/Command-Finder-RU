# Архитектура и разработка

Command Finder RU сохраняет устройство исходного проекта: описания команд индексируются в SQLite, запрос преобразуется в вектор, найденные шаблоны показываются в меню. Модель служит энкодером; команды берутся из словаря.

```text
Запрос пользователя
    → кеш вектора запроса
      └─ при промахе: убрать явные значения путей → локальный ONNX-энкодер, 312 измерений
    → sqlite-vec
    → ближайшие описания и устранение повторов команд
    → извлечение аргументов и заполнение размеченных шаблонов
    → меню выбора
    → строка ввода / stdout / буфер обмена / tmux
```

## Интеграция Bash

`cf --install-shell` печатает пакетный скрипт `data/cf.bash`. Его подключают из `~/.bashrc`; загрузчик `shell/cf.bash` из репозитория использует тот же ресурс. Релизный установщик сохраняет свой загрузчик в `$CF_INSTALL_DIR/cf.bash`, поэтому подключение оболочки не зависит от checkout репозитория.

В рекомендуемой команде установки `&& source ~/.bashrc` выполняется в родительском интерактивном Bash после успешного завершения установщика. Это сразу активирует интеграцию в текущем терминале. Вызов `source` внутри дочернего `bash`, запущенного через конвейер, не изменил бы окружение родительской оболочки. Для нестандартного `CF_BASHRC` установщик печатает команду с выбранным путём.

В интерактивном Bash 4+ горячая клавиша `Ctrl+F` вызывает обработчик через `bind -x`. Обработчик читает `READLINE_LINE`, передаёт описание задачи CLI и заменяет `READLINE_LINE` выбранной командой; `READLINE_POINT` переводит курсор в её конец. На строке набирают само описание задачи, без префикса `cf`. На пустой строке обработчик сначала запрашивает описание задачи. Меню получает терминал через `/dev/tty`. Отмена или ошибка сохраняет исходную строку, выбранная команда остаётся для ручного редактирования и выполнения.

Обычная функция `cf "запрос"` печатает результат CLI и добавляет выбранную команду во включённую историю интерактивной оболочки, чтобы её можно было вернуть клавишей `↑`. Информационные флаги и явные режимы `--print`, `--copy`, `--tmux` передаются CLI напрямую. Подключение не заменяет `PROMPT_COMMAND` и не исполняет найденную команду. Bash 3.2 не поддерживает нужный механизм подстановки; самостоятельный CLI остаётся доступным без интеграции.

## Модель и артефакт

Рабочая модель — `sergeyzh/rubert-mini-retriever`, ревизия `4ae6298c749e413b958d64a4b349a907c15a3b54`. Выбран 8-битный вариант U8U8 с динамическим квантованием ONNX Runtime. Полный граф включает энкодер, pooling и L2-нормализацию. Выход `sentence_embedding` имеет форму `[batch, 312]` и тип float32; входы допускают разные размеры пакета и длины последовательности.

Готовый каталог содержит `model.onnx`, `tokenizer.json` и `metadata.json`. Метаданные задают идентичность модели, ревизию, размерность, тип квантования, предел длины и настройки токенизации. В рабочем профиле длина ограничена 128 токенами, префиксы запросов и описаний пустые.

Индекс и запросы должны использовать один артефакт и одинаковую обработку текста. Векторы документов из одной модели нельзя смешивать с запросами другой модели или варианта квантования. При замене артефакта следует перестроить индекс.

Первоначальная сборка требует отдельных зависимостей `.[export]`: PyTorch CPU, Sentence Transformers, Transformers и ONNX. Поиск использует NumPy, Tokenizers и ONNX Runtime. Получение модели и экспорт отделены от обычного запуска CLI.

`cf --prepare-model --model-source <каталог>` импортирует уже подготовленный локальный артефакт. Релизный `install.sh` скачивает готовые модель и базу из GitHub Release; тяжёлую подготовку он не запускает. Для сборки из исходников в отдельном окружении:

```bash
python3.12 -m venv .model-build.manual
.model-build.manual/bin/python -m pip install 'torch==2.6.0' --index-url https://download.pytorch.org/whl/cpu
.model-build.manual/bin/python -m pip install -e '.[export]'
.model-build.manual/bin/cf --prepare-model
```

Каталог `.model-build.manual` предназначен для временной подготовки и не нужен при поиске; его следует удалить после успешного экспорта. Если одновременно используется релизная установка, задайте отдельные `CF_DB_DIR` и `CF_MODEL_DIR` для разработки.

## Каталоги и конфигурация

Без релизного загрузчика база по умолчанию располагается в `~/.local/share/cf-ru/cf.db`, артефакт — в `~/.local/share/cf-ru/onnx`, кеш описаний — под каталогом данных. Отдельное имя `cf-ru` сохраняет старые данные исходного приложения с векторами размерности 384.

Релизная установка использует корень `CF_INSTALL_DIR` (по умолчанию `~/.local/share/cf-ru`) и следующую структуру:

```text
cf-ru/
  cf                  — загрузчик команды
  cf.bash             — загрузчик Bash-интеграции
  uninstall.sh        — удаление без checkout репозитория
  install.json        — маркер принадлежности каталога установщику
  current -> releases/<версия>.<суффикс>
  releases/<версия>.<суффикс>/
    venv/             — окружение, созданное сразу по окончательному пути
    data/cf.db        — готовая база конкретного выпуска
    model -> <корень установки>/models/<идентификатор>
  models/<идентификатор>/
    model.onnx
    tokenizer.json
    metadata.json
    checksums.json
```

Загрузчик `cf` устанавливает `CF_DB_DIR` в `current/data` и `CF_MODEL_DIR` в `current/model`, если пользователь не задал их явно. Символическая ссылка `~/.local/bin/cf` ведёт на этот загрузчик. Окружение не перемещается после создания: пути Python-скриптов остаются корректными. Модель хранится отдельно от выпусков и может использоваться повторно при обновлении словаря.

При первой установке корневой каталог должен отсутствовать или быть пустым; непустой каталог без маркера этой установки отклоняется. Это сохраняет посторонние файлы и данные прежней установки из checkout. Для перехода освобождают старую ссылку команды и выбирают отдельный пустой каталог.

Удаление без `--purge` убирает окружения, команду и интеграцию, сохраняя базы, модели и сам скрипт удаления. `--purge` удаляет управляемый каталог целиком. Указанные пользователем внешние `CF_DB_DIR` и `CF_MODEL_DIR` установщик и удаление не заменяют и не удаляют.

Основные переменные описаны в README. `CF_MODEL`, `CF_MODEL_REVISION` и `CF_EMBEDDING_DIM` участвуют в проверке идентичности, но не отменяют закрепление рабочей модели. Подготовка проверяет артефакт по `data/model.json`. Смена модели требует согласованного изменения этой спецификации, подготовки нового артефакта и переиндексации; обычному пользователю менять переменные идентичности не требуется.

## Данные и схема

```text
commands(id, name, category, synopsis, description)
patterns(id, command_id, pattern_type, text, command_template, explanation, destructive, arguments)
pattern_embeddings  — vec0, embedding FLOAT[312], ключ pattern_id
query_cache         — векторы запросов для текущего индекса
```

Дополнительные метаданные индекса фиксируют его совместимость с моделью и источником данных. При несовпадении индекса приложение должно предложить переиндексацию, а не выполнять поиск в чужом векторном пространстве.

Описание `pattern.text` индексируется отдельно. Шаблон `pattern.command` нужен для показа и вывода; энкодер не исполняет его. Устранение повторов выполняется по точной строке шаблона команды. Для повторных записей опасный признак сохраняется, если он установлен хотя бы у одной из них.

## Индексация

`seed_database()` сохраняет пакетный порядок обработки:

1. Загружает JSON по категориям.
2. Объединяет команды по `(category, name)` и собирает метаданные описаний.
3. Вызывает пакетный `encode_batch()` для текстов, внутри которого модель обрабатывает ограниченные пакеты.
4. Пакетно вставляет команды, описания и соответствующие им векторы в SQLite.
5. Восстанавливает настройки SQLite, завершает транзакцию и сохраняет метаданные индекса.

При `--seed --force` векторы вычисляются до замены таблиц; замена схемы и пакетная загрузка проходят в одной транзакции. Ошибка кодирования или вставки сохраняет прежнюю базу. Обычный `--seed` не добавляет повторно уже загруженные описания.

Кеш векторов описаний зависит от содержимого файлов модели и токенизатора, метаданных, параметров кодирования и упорядоченного списка текстов. Для динамического квантования учитывается размер пакета. Это позволяет повторно использовать подходящие векторы при перестроении базы.

Кеш запроса проверяется до загрузки энкодера. Для повторной команды модель может вообще не загружаться. Идентичность индекса связывает такой кеш с моделью, на которой он был получен. Ключ сохраняет регистр, порядок слов, внутренние пробелы и отрицания; убираются только пробелы по краям запроса. При штатном обновлении артефакта смена манифеста контрольных сумм обнаруживается при открытии базы без чтения всех весов при каждом запросе.

## Добавление команд

Один файл JSON соответствует одной категории; поле `category` должно совпадать с именем файла.

```json
{
  "category": "my_tools",
  "commands": [
    {
      "name": "mytool",
      "synopsis": "mytool [options] <file>",
      "description": "Проверка файлов собственным инструментом",
      "patterns": [
        {
          "type": "example",
          "text": "проверь файл моим инструментом",
          "command": "mytool --check <file>",
          "explanation": "Проверяет файл и выводит результат проверки",
          "destructive": false
        }
      ]
    }
  ]
}
```

- `name` и `synopsis` сохраняют реальное имя и синтаксис инструмента.
- `description`, `text` и `explanation` пишутся по-русски.
- `text` формулируется как намерение пользователя. Для сценария полезны разные формулировки.
- `command` должен выполнять описанную задачу. Конкретные пути и имена должны быть понятными примерами или параметрами.
- `destructive: true` отмечает удаление данных, завершение процессов, перезапись истории, форматирование и другие труднообратимые действия. Признак не следует устанавливать на каждую команду только из-за её административного назначения.

После изменения JSON:

```bash
python -m json.tool src/cf/data/commands/my_tools.json
cf --seed --force
cf "проверь файл моим инструментом"
python -m pytest
```

Число команд и описаний в README обновляется при изменении покрытия. Не редактируйте производную базу вручную и не переходите к вставкам по одной строке.

## Аргументы шаблонов

Необязательное поле `pattern.arguments` связывает параметры команды с их ролями:

```json
{
  "type": "example",
  "text": "упаковать папку в архив tar.gz",
  "command": "tar -czf <archive> -- <source>",
  "arguments": {"archive": "archive", "source": "source"}
}
```

Роли: `path` — единственный файл или каталог; `source` — источник; `destination` — назначение; `archive` — имя архива. Имена параметров имеют вид `[a-z][a-z0-9_]*`, каждая роль встречается один раз, повторное использование одного параметра в шаблоне допустимо. Каждый параметр занимает отдельное слово вне кавычек. Для непустого `arguments` набор имён должен точно совпадать с `<name>` в команде. Шаблоны без разметки сохраняют обычное поведение.

`seed.py` проверяет разметку до кодирования и замены индекса, сохраняет её как JSON в `patterns.arguments` вместе с остальными полями пакетной записью. При открытии старой базы добавляется пустая колонка: поиск продолжает работать, а для загрузки новой разметки из словаря нужна переиндексация. Векторное пространство и размерность не меняются.

Разбор аргументов использует явные пути, кавычки, имена с расширениями и контекст «файл/папка/каталог/архив», «из/в». Программа не проверяет существование путей и не выполняет выражения shell. Неоднозначные значения остаются параметрами; управляющие символы и незакрытые кавычки отключают подстановку. Значения экранируются через `shlex.quote`, с отдельной обработкой `~/` и имён, начинающихся с `-`.

Для поиска `search_query()` убирает явные значения путей из текста запроса, сохраняя формат архива и маски файлов. Это уменьшает влияние конкретных имён на выбор операции; для подстановки используется полный исходный запрос. Названия без контекста пути, например `node.js`, сохраняются. Ключ кеша по-прежнему содержит весь исходный запрос и использует пространство `v3`, поэтому векторы прежнего алгоритма не переиспользуются.

Поиск устраняет повторы по исходному шаблону. `SearchResult.command_template` хранит его для диагностики, `command` возвращает заполненную строку, `missing_arguments` перечисляет оставшиеся параметры. Обе версии меню, подтверждение опасной команды и все режимы вывода используют одну заполненную строку. В базе и кеше сохраняются шаблоны и векторы, подстановка вычисляется заново для каждого запроса.

## Проверки и выпуск

```bash
python -m pip install -e '.[dev]'
python -m pytest
python -m build
```

Обычные тесты используют небольшие фиктивные ONNX-графы, временные базы и подменённые внешние команды. Для них не нужны загрузка весов и GPU. Отдельная интеграционная проверка готового рабочего артефакта должна включать индексацию, обычный запрос, повторный запрос с кешем и запрос после запуска нового процесса.

В Git сохраняются исходники, словарь, тесты, спецификация модели, инструкции и компактные результаты сравнения. Веса, базы, кеши, `.venv`, каталоги сборки и машинные журналы остаются локальными. Лицензия кода и атрибуция исходного проекта находятся в `LICENSE` и README; модель распространяется по собственной лицензии MIT.

## Релизная сборка

Обычный push и pull request запускают проверки без публикации и подготовки тяжёлых артефактов. Отдельный workflow `.github/workflows/release.yml` запускается по отправке тега:

- `vX.Y.Z` — стабильный GitHub Release;
- `vX.Y.Z-rcN` — GitHub Pre-release;
- остальные имена не являются релизными версиями.

Версия тега должна соответствовать версии в `pyproject.toml` и `cf.__version__`; например, тегу `v1.1.0-rc1` соответствует Python-версия `1.1.0rc1`. Сначала изменяют версии, коммитят изменения и только затем отправляют тег. Предварительные выпуски серии 1.1 используют формат `v1.1.<patch>-rc<номер>`. Пример выпуска:

```bash
git tag v1.1.0-rc1
git push origin v1.1.0-rc1
```

CI собирает wheel и исходный архив, подготавливает закреплённую ONNX-модель, создаёт базу из JSON-словаря и проверяет поиск. Перед упаковкой база получает пустой кеш запросов, все записи WAL переносятся в основной файл, соединения закрываются. Готовая база и модель проверяются с закреплёнными зависимостями Python 3.12 и 3.13 на Linux x86_64.

Релиз содержит wheel, исходный архив, архив модели, архив базы, закреплённый список runtime-зависимостей, `release.json`, `SHA256SUMS` и скрипты установки/удаления. Манифест связывает файлы одного выпуска и их контрольные суммы; идентификатор модели позволяет повторно использовать неизменившийся артефакт. PyTorch и остальные зависимости экспорта остаются в CI. Runtime-зависимости устанавливаются с PyPI через `pip` с запретом сборки из исходников; wheelhouse в релиз не включается.

Установщик по умолчанию выбирает последний стабильный релиз, затем фиксирует его тег для всех скачиваний. `--version vX.Y.Z-rcN` позволяет явно выбрать предварительный выпуск; его установщик скачивают из `/releases/download/<тег>/install.sh`, чтобы установка RC работала и до первого стабильного релиза. Он проверяет манифест и контрольные суммы, создаёт окружение и распаковывает проверенные артефакты. Выпуск становится активным после успешной проверки; ошибка новой установки сохраняет ранее выбранную версию. Архивы загрузки и временные файлы удаляются. Обычная установка не вызывает экспорт модели или `cf --seed`.
